# GitLab MR Radar — анализ кода и доработки 1.4.0 (2026-10-27)

Основа: README, `swarm-report/roadmap-research-2026-10-26.md`, весь `src/`. Результат — релиз v1.4.0 (6 коммитов + `Version 1.4.0`), саморевью каждого блока агентом `code-reviewer` до READY-TO-PUSH.

## Исходные вопросы
- Уведомление «можно мёржить» было завязано только на `detailed_merge_status === 'mergeable'`, без учёта CI.
- Подписки на статусы нет — только опрос по `chrome.alarms` (интервал 1–120 мин, по умолчанию 5). Push невозможен без серверного ретранслятора (вебхуки) или внутреннего ActionCable API GitLab.

## Добавленные возможности
- Адаптивный опрос: раз в минуту, пока идёт CI / `ci_still_running` / пересчёт статуса, не дольше 60 мин подряд; отключается галкой.
- Уведомления по типам (отключение отдельных событий).
- Тихие часы (+ выходные): события копятся в `pendingNotifications`, после окончания — одно уведомление с ещё актуальными; события с недоступным источником ждут следующего обновления.
- Snooze «до утра» пропускает выходные, новый вариант «до понедельника».

## Найдено саморевью (исправлено до коммита)
- Блок C: `hasActivePipelines` считался после стабилизации статусов → пересчёт статуса не включал быстрый опрос. Теперь считается по сырому ответу.
- Блок E: неизвестный `reviewState` (REST-фолбэк) давал ложное уведомление «на ревью». Введено различие `undefined` (неизвестно) / `null` (нет состояния) + перенос последнего известного; фолбэк запроса только на ошибку схемы.
- Блок D: отложенные события с недоступным источником показывались бы с устаревшими данными — разделены на `relevant` / `waiting`.

## Не сделано
- Chrome Web Store — нужен аккаунт разработчика.
- ESLint / `checkJs` — проект без зависимостей; без lock-файла это supply-chain риск. Возможно при согласии на `package-lock`.
- Оптимизация числа запросов на Maintainer-проекты (GraphQL вместо REST по проекту) — сначала посмотреть метрику.
- Тесты `onAlarm` / `onInstalled` / `onStartup` путей.

## Непроверенное (по памяти, сверить на целевом инстансе)
- `with_merge_status_recheck` действительно снимает `unchecked` в list-API.
- `reviewers.mergeRequestInteraction.reviewState` доступен в используемой версии GitLab (Free); `REQUESTED_CHANGES` — примерно 16.x+.
- Новый push не сбрасывает `reviewState` — MR с замечаниями вернётся в счётчик только после «запросить ревью повторно».
- Тип уведомления `list` на macOS показывает только title/message.

## Риски / отступления
- Агент `lmwork-reviewer` недоступен — саморевью выполнял `code-reviewer`.
- `reviewed` трактуется как «ход автора»; если автор пушит без повторного запроса ревью, MR не попадёт в счётчик (ответы в тредах всё равно видны в секции тредов).
- Стабилизированный merge-статус переносится без ограничения по времени, пока GitLab отдаёт переходный статус.
